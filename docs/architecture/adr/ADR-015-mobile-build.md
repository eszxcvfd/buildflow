# ADR-015 — Mobile Build & Distribution Strategy

Status: Accepted

Date: 2026-09-02
Decision owners: Project Owner / BuildFlow Team

## Context

The Mobile application (`apps/mobile`) must be built and distributed for testing on physical Android devices, emulators, and final project defense presentations. Local manual native compilation (Android Studio / Gradle / NDK) across different developer machines frequently suffers from environment discrepancies, missing SDK licenses, and high build times. We need a standardized, reproducible build and distribution strategy.

## Decision

We adopt **EAS Build (Expo Application Services)** as the official build and packaging pipeline for `apps/mobile`.

### Build Profiles (`eas.json`)

We configure three standard build profiles:

1. **`development`**:
   - Generates a custom development client build (`.apk`) containing all native modules and Expo debug tooling for active feature development.
2. **`preview`**:
   - Generates a standalone, production-like installable Android **APK (`.apk`)**.
   - Used for internal testing on physical Android 10+ devices, user acceptance testing (UAT), and thesis defense demonstrations.
3. **`production`**:
   - Generates an optimized Android App Bundle (`.aab`) configured for release signing.

### Scope & Distribution Rules

- **Android 10+ Focus**: Builds target Android 10+ (API level 29+) in alignment with `NFR-CMP-002` and `CR-001/Q-14`.
- **Direct APK Distribution**: For defense and testing, the standalone APK generated by the `preview` profile is distributed directly to test devices (or via internal distribution links).
- **No Mandatory Play Store Publishing**: Public Google Play Store publication is **not required** to satisfy the capstone defense baseline.

## Alternatives considered

- **Manual Local Gradle Builds (`npx react-native run-android`)**: Rejected as the primary distribution mechanism due to host OS discrepancies and heavy local Android build toolchain requirements for all team members.
- **Fastlane with Bare Native Projects**: Rejected due to high configuration overhead compared to EAS Build integration with Expo SDK 57.

## Consequences

### Positive

- Clean, cloud-hosted or reproducible local builds that generate ready-to-install Android APKs.
- Eliminates native compilation environment conflicts on developer workstations.
- Simple, reliable artifact generation for the project defense.

### Negative / trade-offs

- EAS cloud builds require an Expo account and internet connectivity during build triggering.

## Constraints

- Mobile acceptance verification is conducted on Android 10+ APK builds.
- iOS App Store distribution is strictly out of scope for V1.
